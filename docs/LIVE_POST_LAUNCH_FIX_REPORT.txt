2. AUTHENTICATION ROOT CAUSE
--------------------------------------------------------------------------------

Confirmed root cause: implicit-flow / PKCE mismatch plus unsafe failure redirect.

Evidence chain (redacted):
  • Google OAuth succeeded and Supabase issued session material.
  • Browser Supabase client had detectSessionInUrl: true without flowType: 'pkce'.
  • Supabase returned tokens in the URL fragment (#access_token=…), while the
    server callback only handled ?code= via exchangeCodeForSession.
  • Server callback saw no code → redirected to /signup?error=google.
  • Legacy implicit hash could remain visible in the browser bar/history alongside
    the error query string (incident pattern: /signup?error=google#access_token=…).

Contributing factors:
  • No @supabase/ssr server exchange client; ad-hoc supabase-js with
    persistSession: false only.
  • Failure paths put provider hint (error=google) in the URL.
  • console.error in callback logged auth failure messages.
  • redirectTo/origin sometimes derived from request URL rather than configured
    public site origin in production mode.


2B. PRODUCTION LOCALHOST OAUTH CALLBACK (CONFIRMED ROOT CAUSE — P0)
--------------------------------------------------------------------------------

Symptom (production):
  Google OAuth authorize URL contained
  redirect_to=http://localhost:3000/auth/callback?next=/profile
  instead of redirect_to=https://questionwale.com/auth/callback?next=/profile.

Confirmed root cause (two linked failures):

  A) Client-side OAuth start (removed):
     HomeGoogleCtaButton previously called signInWithOAuth in the browser via
     getClientOAuthOrigin(), which read NEXT_PUBLIC_SITE_URL without rejecting
     localhost in production. That public env var is baked at build time; a
     production deployment built with .env.local (localhost) embedded localhost
     into the client bundle even when users visited questionwale.com.

  B) Server-side origin is now authoritative but required redeploy:
     getTrustedPublicOrigin() in lib/publicOrigin.ts rejects localhost when
     NODE_ENV=production or VERCEL_ENV=preview|development, and never reads Host,
     Origin, Referer, x-forwarded-host or request query parameters. OAuth start
     moved to GET /api/auth/google/start which builds redirectTo server-side via
     lib/oauthCallback.ts → buildOAuthCallbackForRequest().

Profile page not showing after login (secondary root cause):
  PKCE code_verifier cookies from signInWithOAuth were set via cookies() but not
  attached to the 302 redirect response (same class of bug as qw_auth). Code
  exchange at /auth/callback failed silently → flash redirect to /login → profile
  never received qw_auth session. Fixed by applyPendingSupabaseCookies() on OAuth
  start and attachAuthCookie() + clearSupabaseAuthCookiesOnResponse() on callback.
  ProfileClient infinite /api/profile loop fixed with loadedForUserRef guard
  (removed refreshUser() from loadProfile()).

Authoritative origin strategy:
  • Single canonical variable: NEXT_PUBLIC_SITE_URL (validated HTTPS in prod).
  • getTrustedPublicOrigin() — server-only; throws PublicOriginConfigError if
    missing/invalid in production; never falls back to localhost in production.
  • buildOAuthCallbackUrl() / buildOAuthCallbackForRequest() — shared callback
    builder; validates origin + getSafeRedirectPath() for internal next paths.
  • All Google login buttons navigate to /api/auth/google/start?next=… (no client
    signInWithOAuth, no getClientOAuthOrigin).

Expected callback origins after fix:
  Production: https://questionwale.com/auth/callback?next=%2Fprofile
  Local dev:  http://localhost:3000/auth/callback?next=%2Fprofile

Proof production cannot fall back to localhost:
  • lib/publicOrigin.test.ts: production with NEXT_PUBLIC_SITE_URL=localhost → throws
  • lib/publicOrigin.test.ts: production with empty NEXT_PUBLIC_SITE_URL → throws
  • Runtime simulation (NODE_ENV=production, NEXT_PUBLIC_SITE_URL=https://questionwale.com):
    origin=https://questionwale.com, callback=/auth/callback?next=%2Fprofile,
    prod_has_localhost=false

Proof Host-header injection cannot alter callback:
  • lib/publicOrigin.test.ts: request with host/x-forwarded-host=evil.example still
    resolves https://questionwale.com

Local-mode runtime check (@ localhost:3000 dev server):
  GET /api/auth/google/start?next=/profile → HTTP 302
  redirect_to parameter origin = http://localhost:3000 (expected in dev)
  set-cookie: sb-*-auth-token-code-verifier present on redirect (PKCE fix verified)

Production-mode simulation (no live OAuth URL printed):
  redirect_to would encode https://questionwale.com/auth/callback — no localhost

3. OLD FLOW VS NEW FLOW
--------------------------------------------------------------------------------

OLD:
  1. signInWithOAuth (implicit-capable browser client, detectSessionInUrl: true)
  2. Return to /auth/callback#access_token=… OR missing ?code=
  3. Server cannot read hash → redirect /signup?error=google
  4. Tokens may remain in browser URL/history

NEW:
  1. signInWithOAuth with flowType: 'pkce', detectSessionInUrl: false
  2. redirectTo = {origin}/auth/callback?next={safe-internal-path}
  3. Supabase returns short-lived ?code= only (never tokens in fragment)
  4. GET /auth/callback (no HTML) → @supabase/ssr exchangeCodeForSession(code)
  5. Upsert app user → set qw_auth httpOnly cookie → clear transient sb-* cookies
  6. 302 to clean internal path (default /dashboard) — no query, no hash
  7. Failures → one-time flash cookie → 302 to /login (clean URL)
  8. Login/signup mount AuthHashGuard → strips legacy #access_token hashes
